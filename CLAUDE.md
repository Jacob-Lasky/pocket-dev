# pocket-dev

Browser-accessible terminal for Claude Code. Node + Express server (`mobile/server.js`) hosts N independent tmux sessions — each its own pty, each surfaced as its own xterm.js instance in a single browser tab. The session list switches between them; only one is visible at a time, but each retains its own main-buffer scrollback so browser scroll (wheel + touch) never shows the wrong session's history. Runs as a Docker container on UnRAID; image is `ghcr.io/jacob-lasky/pocket-dev:latest` published from `.github/workflows/docker-publish.yml` on push to main and on a weekly schedule.

## Per-session model — why it exists

An earlier architecture multiplexed everything through one tmux session, one pty, one xterm.js. Switching tmux windows (`Ctrl-b n`) painted the new window into the same xterm.js main buffer, so the browser's scrollback was the *union* of every window's output — you couldn't scroll back into "this window's history" because there was no such thing in the browser.

The fix was structural: each toolbar tab is a real isolated session with its own pty, its own tmux session (named `${TMUX_SESSION}-1`, `-2`, …), and its own xterm.js with its own main-buffer scrollback. Switching tabs is now a pure DOM toggle. The bleed is impossible because the bytes never share a buffer.

`mobile/test/e2e/sessions.spec.js` is the regression guard. If you flatten the architecture back to one xterm.js, that spec fails.

## Two layers of alt-screen — disable only the OUTER one

**This is the most non-obvious thing about this codebase. Re-read it before touching `mobile/tmux.conf` or anything serialize-related.**

There are two independent "alternate screen" mechanisms in play. They are NOT the same thing:

1. **Outer alt-screen**: tmux switching the visible buffer it shows to xterm.js when a session attaches. Tmux does this by default — it sends `\x1b[?1049h` (smcup) on attach. Result: every byte of session output lands in xterm.js's alt-buffer, which has no scrollback.

2. **Inner alt-screen**: applications running INSIDE tmux (Claude Code's TUI, vim, less, htop) using alt-screen for their own full-screen UI.

We **disable the outer** so all output lands in xterm.js's normal buffer (which the copy helper reads by walking `term.buffer.normal`, see `view.js`; for a plain shell this is continuous scrollback, for a TUI coder it is the current frame — see "Mobile scroll + live selection"). We **must NOT disable the inner** — Claude Code renders its prompt input area inside an alt-screen TUI; disabling inner alt-screen breaks input handling entirely (user can't type).

The `mobile/tmux.conf` knobs:

| Setting | Layer | Want? |
|---|---|---|
| `set -ga terminal-overrides ',xterm*:smcup@:rmcup@'` | OUTER — strips smcup/rmcup from outer terminfo, tmux can't switch buffers there | ✅ Keep |
| `setw -g alternate-screen off` | INNER — tells tmux to forbid inner apps from alt-screen | ❌ NEVER add this back |
| `set -g focus-events on` | Forwards focus events into inner apps | ✅ Keep |

`mobile/test/server/tmuxConf.test.js` has a regression-guard test that asserts `alternate-screen off` is NOT in the file. If you find yourself wanting to disable inner alt-screen, you're chasing the wrong fix.

## Test gap: cat doesn't exercise alt-screen

The E2E fixture sets `SHELL_CMD=cat` for deterministic echo behavior. **Cat doesn't use alt-screen**, so any regression that affects only TUI apps (anything with a curses-style prompt — Claude, vim, htop) won't surface in CI. The `setw alternate-screen off` mistake shipped through CI green for this reason.

To partly close this gap, `mobile/test/e2e/fixtures/claude-trust-frame.b64` is a captured real Claude TUI frame (the "trust this folder?" prompt, which positions words with CHA absolute-column moves and emits no literal spaces). `view.test.js` replays it through a real xterm to assert the copy helper reconstructs the spaces, and `view-claude-frame.spec.js` replays it through the full server (via `SHELL_CMD=bash replay-claude-frame.sh`) for a browser-level check. This covers the alt-screen render path that cat cannot.

If you change anything in the buffer / copy / selection / focus / alt-screen path, still manually verify against the deployed Claude before declaring success. The `mobile/MANUAL-VERIFICATION.md` checklist exists for this.

## Architecture cheat sheet

- **Server** (`mobile/server.js`): exports `buildTmuxSpawnArgs`, `buildSessionCommand`, `createApp`, `createSessionsApi`, `refreshTmuxSession`, `readCodexTurnStatuses`, `readCodexTurnStatus`, `TMUX_CONF_PATH`, `LAUNCHER_PATH`, `CODEX_LAUNCHER_PATH`, `CODEX_HOOK_PATH`, `CODEX_STATUS_PATH`, `SAFE_ID`, `GONE_CODE`. Auto-boots only when run directly (`require.main === module`); requiring it for tests does nothing.
  - **`createApp({ sessionsApi })`**: returns an Express app. Session-aware routes (`GET/POST/DELETE /sessions`, plus `/send /key /refresh /viewed`) only wire up if `sessionsApi` is passed; the static `render.spec.js` boots `createApp()` with no api on purpose to get an unwired test surface.
  - **`createSessionsApi({ store, spawnPty, killSession, refreshSession, projectsDir, logger, codexTurnStatuses })`**: stateful factory holding `Map<id, SessionState>`. Each session owns a pty, a 512 KB replay buffer, and the set of connected WebSocket clients. `attachWs(ws, sessionId, { frames })` wires an upgraded WS into the matching session, replays buffered bytes, and then asks tmux for its authoritative current screen because the bounded byte suffix may begin inside a differential TUI frame — `frames` picks JSON output frames over raw bytes, see "Terminal replies across reconnects". Every option is injectable and defaults to inert or real-world: `store` defaults to `nullSessionStore` (no filesystem side effects unless asked), `spawnPty` to the real tmux spawn, `killSession` to a real `tmux kill-session`, `refreshSession` to the real `refreshTmuxSession`, and `codexTurnStatuses` to the bounded batch App Server helper. Tests swap them rather than mocking modules, same shape as `createApp({ sessionsApi })`. `killSession` and `refreshSession` are injectable because their defaults shell out to a tmux server the tests do not own: a kill destroys a developer's session (see "Archiving a conversation somewhere else closes its tab here"), and a refresh would fire on every reconnect in the pty-backed e2e fixtures, which have no tmux client at all.
  - **`restore()`**: re-creates the sessions in the roster, before `listen()`. See "Session restore".
  - Endpoints: `GET /sessions` (list), `POST /sessions` (create + return id), `DELETE /sessions/:id` (terminate), `POST /send { session, text, bracketedPaste }`, `POST /key { session, key }`, `POST /refresh { session }`, `/ws?session=<id>&frames=1&grid=1` upgrade. `frames=1` selects JSON output frames; `grid=1` advertises that the browser understands grid frames, and stays separate so an open pre-grid browser can reconnect to a new server without rendering unknown JSON as terminal text. `bracketedPaste` wraps the text in `\x1b[200~`/`\x1b[201~` (with any embedded ESC stripped) so a multiline composer message arrives as ONE prompt; the browser sets it only when xterm reports the inner app negotiated the mode. No `/tmux-kill` — replaced by `DELETE /sessions/:id`. No `/history` — copying reads parsed cells client-side.
  - `SAFE_ID = /^[A-Za-z0-9._-]+$/` guards every session id that touches shell interpolation (notably the tmux refresh, which lists tmux clients via shell pipe). `refreshTmuxSession` re-tests the id itself rather than trusting its callers, because it now has two of them — `POST /refresh` behind `requireSession`, and `attachWs` reading the id off the socket's query string — and it is the function that owns the interpolation. `endpoints.test.js` pins both the command it builds and the rejection of an unsafe id before any shell runs.
- **Server-side modules**: `safeId.js` (the shared `SAFE_ID` / `UUID_RE` guards — one definition, several consumers, including the Codex `SessionStart` hook and the pre-upgrade binding helper), `sessionStore.js` (the on-disk roster + per-session provider conversation uuid), `claudeSession.js` (read-only inspection of Claude's transcripts: find one by uuid, classify busy/idle/asking/unknown, identify which turn that verdict came from, and spot the Remote Control archive notice), `codexAppServer.js` (the bounded JSON-RPC client shared by migration and restore status), and `codexTurnStatus.js` (the supported status vocabulary and restore classifier). `claudeSession.js` exports `findTranscript`, `classifyTranscript`, `inspectTranscript`, `USER_INPUT_TOOLS`, `STATUSES`, `WANTS_USER`, `TURN_SETTLED` and deliberately no uuid-level convenience wrappers: the two that existed (`statusOf`, `inspect`) re-resolved the path per call, which is what `describe()`'s memo cache exists to avoid, and once the server stopped calling them their only callers were their own tests.
- **Helpers shipped beside the server**: `pd-claude-session` and `pd-codex-session` (one per-session restart loop + resume decision each), `pd-codex-session-start` (the managed Codex `SessionStart` hook — node, not shell, because it shares `safeId.js` with the server), `pd-codex-bind-current` (one-time pre-upgrade binding for a Codex tab older than the hook), `pd-codex-thread-status` (reads only the newest persisted turn through App Server, with its thread id on stdin and no diagnostic channel), and `pd-trust-workspace` (clears the workspace-trust gate at boot). The Codex helpers share `codexAppServer.js` rather than carrying two protocol clients. Every helper invoked by absolute path has a load-bearing exec bit asserted in tests.
- **Client modules** (`mobile/public/js/*.js`, all ESM):
  - `clipboard.js` — `clipboardWrite` strips trailing whitespace, falls back to `document.execCommand('copy')` on HTTP where `navigator.clipboard` is unavailable. That fallback restores the previously focused element after its scratch textarea goes away, so a copy does not take the keyboard off the composer.
  - `view.js` — `renderTerminalText` walks the active session's parsed `term.buffer.normal` cells for whole-screen copy, preserving real spaces and rejoining soft-wrapped rows (`{ viewportOnly: true }` limits it to the rows on screen). `cleanCopyText` normalises copied text. NO serialize/ansi_up (the note at the top of the file and "Common gotchas" below say why). No HTML renderer and no palette any more: colour is xterm's job now.
  - `selection.js` — `LiveSelection` keeps selection inside xterm: an ordinary mouse drag over a mouse-tracking TUI becomes xterm's own forced selection while a click still reaches the app, and touch gets long-press selection, drag handles, and a Copy/Done menu through the public selection API.
  - `scroll.js` — mobile Live touch-scroll helpers: `scanMouseState` (fold a WS chunk into `{track,sgr}`), `wheelSequence` (SGR/X10 wheel bytes), `wheelStepsFromDelta` (drag px → whole wheel steps). Pure; the DOM wiring lives in `index.html`'s `installTouchScroll`.
  - `attention.js` — what wants the user: `rowState` (the four-state model), `wantsUser`, `badgeState` (the two Sessions-button tiers), `pollDelay`, `summarise`, `STATE_TEXT`. Pure and unit-tested, which is the point: this logic was inline in `index.html` where nothing could check it, and it was wrong three ways at once. `index.html` binds `activeId` into two one-line wrappers and holds no rules of its own.
  - `keys.js` — `maybeInterceptCopyKey` for `term.attachCustomKeyEventHandler`. Selection-aware Ctrl+C + always-copy Ctrl+Shift+C.
- **`index.html`**: monolithic by design. Inline `<script type="module">` with imports; toolbar functions exposed on `window` via `Object.assign` so HTML `onclick` attrs can find them. The `mobile/test/unit/onclick-coverage.test.js` test parses the file and asserts every `onclick="X("` resolves to an exposed name — this catches the "scope-leaked-after-converting-to-module" regression class.

## Mobile scroll + live selection — what the buffer actually holds

**Measured reality (verify before theorising).** With a full-screen TUI coder (Claude Code) running, xterm.js's `buffer.active` IS `buffer.normal` (the outer smcup strip means xterm never enters an alt buffer) and that buffer holds **exactly one screen — zero scrollback**. tmux flattens the coder's inner alt-screen and repaints it in place via cursor addressing, so no history accumulates in ANY browser buffer. The back-and-forth transcript lives *inside the coder* and is reached only by telling the coder to scroll. Confirmed by driving real `claude` through the pipeline and inspecting the buffer (40 rows, `baseY 0`).

Consequences that shape the UI:

- **Live is the one primary surface, and it is touch-scrollable** (`scroll.js` + the `installTouchScroll` wiring in `index.html`). A one-finger vertical drag is intercepted capture-phase and routed: if the inner app has mouse tracking on (a TUI coder) it is forwarded as SGR wheel events to the pty (the coder scrolls its own transcript — this is exactly what a desktop mouse-wheel does); if not (a plain shell) it scrolls xterm's real scrollback locally. A per-session `mouse` flag (fed by `scanMouseState` on every WS chunk) picks the branch. `tmux.conf`'s `mouse off` is load-bearing for the forward path (lets the coder's mouse tracking pass through).
- **Both the "View mode" and the "Select overlay" that replaced it are gone**, along with `mode.js` and the second renderer they needed. Neither could show the history it implied (there is none in the buffer), and the overlay's real job — grabbing text a mouse-tracking TUI steals from selection — is now done in Live itself, so there is one surface and one owner of the cells. `body.dataset.mode` stays pinned to `live`; there is no `#mode-select` button (`Stop`, a `ctrl-c` key, took its place in the toolbar).
- **Selection lives in xterm** (`selection.js`). `LiveSelection` delays a primary mouse-down while the inner app has tracking on and then decides: movement past a few px replays it as xterm's own FORCED selection (Shift off-Mac, Option on Mac — Alt off-Mac means RECTANGULAR selection and must never be forced), a release without movement replays the click through to the TUI. Hover events over a live selection are swallowed capture-phase, because xterm clears selection on user input and a tracking TUI treats hover as input.
- **Touch selection is long press + `term.select` + a Copy/Done menu with two drag handles.** Moving a finger before the hold threshold cancels it and scrolls instead; compatibility mouse events synthesised after a touch must not clear a held selection. A grid resize clears selection because its coordinates no longer mean the same cells. Output keeps streaming under it — this is the current screen, not a frozen transcript.
- **The composer owns text input on a phone** (`#cmd-input` is a growing `<textarea>`, and xterm's hidden textarea is set `readOnly` on touch so a long press cannot summon a second keyboard). Return inserts a line on a coarse pointer, Enter sends on a desktop, Shift+Enter inserts, Ctrl/Cmd+Enter sends either way; Alt+Up/Down (not bare arrows, which now edit the message) walks sent history. Drafts are per session in `sessionStorage` with an in-memory fallback, and are cleared ONLY after a successful `/send` and only if the draft still holds what was sent — a failure leaves the text editable and says so, rather than eating the message.
- `renderTerminalText` reads `.normal` (not `.active`) and reconstructs real spaces from cells (the #12 fix — do NOT reintroduce serialize/ansi_up). Soft-wrapped rows are rejoined so a copy is not chopped at the host PTY width. The `📋` button copies the selection if there is one, else the visible screen.
- **The keyboard's geometry is the `visualViewport` resize handler's job, and NOT the viewport meta's.** The meta tag carries `viewport-fit=cover` (with `env(safe-area-inset-*)` padding on `#topbar` and `#controls`) and deliberately no `interactive-widget` key: WebKit rejects that key with a console error, which `render.spec.js`'s console-error assertion catches on the webkit project — one more thing that would ship green without webkit in the matrix.

Guard tests: `test/unit/scroll.test.js` (mouse-state scan + wheel math), `test/e2e/touch-scroll.spec.js` (drag → wheel forwarded to pty for a mouse-tracking session via `mouse-app.sh`; drag → local xterm scroll + zero wheel bytes for a plain shell), `test/e2e/live-selection.spec.js` (an ordinary drag over `mouse-app.sh` selects text, a click still reaches the app, and — chromium only, via CDP touch — long press, handles, wide glyphs and Copy), `test/e2e/mobile-composer.spec.js` (multiline send, failed delivery, drafts across switches and reloads, two sessions with sends in flight). The forward path can't be exercised by the `cat` fixture (no mouse tracking) — same test-gap shape as alt-screen, and the touch cases only run where Playwright can emulate touch, which is why `MANUAL-VERIFICATION.md` still carries the real-phone list.

`docs/mobile-interface-decision.md` records WHY this was fixed inside the terminal rather than by adopting a chat client (ACP, HAPI, Happy), and what would change that call; `docs/mobile-interface-verification.md` records what was measured against real Claude and Codex during validation. Deployment status is separate from those local checks.

## Terminal replies across reconnects

The browser asks for JSON output frames with `/ws?session=…&frames=1&grid=1`, and the server tags each frame `replay`, `output`, or `grid`. `grid=1` is a separate capability advertisement so a pre-grid browser reconnecting after a server update continues receiving only the frame types it understands. **Replay is paint-only, including output no browser has seen before.** A terminal query sitting in the replay buffer may already have timed out in whatever asked it, so answering it on attach delivers the answer as TEXT — `0;276;0c` appearing in the user's next prompt is the symptom this exists to prevent. Do NOT add a retry, a ledger, or a hand-off of unanswered historical queries: an answer that arrives late is worse than no answer, and tmux already answers an inner application's own DA/DSR queries itself, falling back to its defaults if its outer negotiation times out. (With no browser attached at startup that negotiation can cost tmux its five-second timeout before focus reporting turns on; rendering and inner DA/DSR replies do not wait for it.)

**The replay buffer is byte history, not restorable screen state.** It is bounded to 512 KB and trims at the next newline, which is right for a plain shell and meaningless for a differential TUI: a newline is not a frame boundary, so the kept suffix can start after the erase or cursor state it assumes, and the pane rebuilds duplicated, interleaved rows. `attachWs` therefore sends the replay first and immediately calls the injectable `refreshSession`, whose production implementation (`refreshTmuxSession`) asks every tmux client attached to that session to repaint its authoritative current screen. WebSocket ordering plus the browser's write queue guarantee the complete repaint lands AFTER the context-dependent suffix, so do not move the refresh before `ws.send(replay)`. A session with an empty replay buffer asks for no repaint — there is nothing to repair — and a failed refresh is logged and left there rather than closing the socket. **Do not treat `fitAndResize()` as the repair**: a phone reconnecting at the same orientation and width produces no PTY resize at all, which is exactly the case that broke; switching to desktop mode changed the dimensions and only *happened* to force the missing repaint. Guards: `sessionsRestore.test.js` pins the replay-before-refresh ordering (framed and raw), the empty-session case and the logged failure; `test/e2e/mobile-render-order.spec.js` runs the `pdServerTruncatedTuiFrame` fixture, whose fake outer pty emits a full-screen frame, then evicts it with more than 512 KB of one-row deltas, and asserts a same-grid reconnect ends on one coherent frame.

For each LIVE chunk the server marks the first open framed client as that chunk's sole responder; the others render it and stay quiet. When a responder disconnects the next connected client answers the queries that follow. The client serialises `term.write` through a promise queue so a reply belongs to exactly one chunk, while keyboard, paste, IME, mouse and focus bytes bypass the queue and go straight to the pty.

**Every browser attached to one session uses the same grid.** The PTY has one
authoritative `cols` and `rows`, so letting each browser retain its own xterm
dimensions makes the same cursor-addressed stream mean different cells. A
framed attach therefore receives `grid` before replay, and an accepted resize
broadcasts `grid` to every framed client before `pty.resize()` can trigger a
repaint. The browser orders grid changes, reset, fit, replay and live output on
one terminal-operation queue. Do not make fit a client-local visual choice or
write output outside that queue. `sessionsRestore.test.js` pins the wire order;
`multi-client-grid.spec.js` opens phone and desktop viewports and requires both
xterms to converge.

**Telling a reply from a keystroke needs one internal xterm hook.** xterm 5.5's public `onData` carries no provenance, so `term._core.coreService.onUserInput` — which fires synchronously just before `onData` for human input — is the discriminator, and it is the only private API in the client. Its flag is cleared on every `onData`, and focus reports (`\x1b[I` / `\x1b[O`) are excluded by hand because they originate outside the parser and are not tagged as user input. **Re-verify this hook on any xterm upgrade.** `test/e2e/replay-queries.spec.js` is the guard; it runs on the `pdServerQueryApp` fixture, whose query app sits on an **outer** node-pty rather than inside tmux, because tmux answers an inner app's DA2 itself and would hide the boundary under test.

**Session launch pins its own PATH and its own shell, for the same class of reason.** `buildTmuxSpawnArgs` forwards `PATH` with `-e` and passes `/bin/bash -c <command>` as SEPARATE arguments. A single command string is interpreted by the already-running tmux server's default shell, and a pre-existing fish server rewrites `PATH` during startup — which silently launched a real `claude` instead of the test stub. `serverArgs.test.js` and `titles.spec.js` cover the launch path.

## Session restore — surviving a restart

A container restart used to cost you every tab. The roster lived only in the server process's memory, so after a restart an open browser's reconnect got a 4404 and sat on dead panes; reloading gave you one blank session. Three pieces fix that, and they are separable on purpose.

**1. The roster (`mobile/sessionStore.js`).** `$PD_STATE_DIR/sessions.json` lists the live session ids, rewritten on every create/destroy/exit. `startServer()` calls `sessionsApi.restore()` BEFORE `listen()`, so a reconnecting browser finds its ids already there instead of a 4404 it has to recover from. tmux is deliberately not the source of truth here: its server dies with the container, so after a restart there is nothing to enumerate. Every failure in the store is non-fatal — an unwritable state dir means no restore, never a server that will not boot.

The same `create()` covers both outage shapes, because `buildTmuxSpawnArgs` uses `new-session -A`: if only node died the call REATTACHES to the live tmux session (scrollback and running Claude intact); if the container died it creates a fresh one.

**2. The conversation (`mobile/pd-claude-session`, `mobile/pd-codex-session`).** Restoring a tab is only half of it — the tab needs the conversation it was having. Both providers resume, and each records one stable uuid in `$PD_STATE_DIR/sids/<id>.uuid`. The server reads and deletes that file; it never chooses an id itself. `launcherFor()` in `server.js` maps a resumable provider to its own launcher and THROWS for one it does not recognise, so declaring `resumeConversation: true` without wiring a launcher fails loudly instead of quietly starting the tab in the plain loop with no resume at all.

**The two providers learn that id in opposite directions, and that asymmetry is the shape of this half.** Claude's launcher CHOOSES the uuid and hands it over (`--session-id` on first run, `--resume` after a respawn). Codex chooses its own, so pocket-dev has to be TOLD: `mobile/pd-codex-session-start` is a `SessionStart` hook that writes the `session_id` Codex reports, and the launcher resumes it with an explicit `codex resume <uuid>`. The hook rides every `SessionStart`: `startup` captures only an empty binding, `resume` and `compact` preserve it, and `clear` atomically replaces it because `/clear` intentionally starts a new conversation without exiting the process.

**That hook is installed as a MANAGED hook, from the image, and that is the load-bearing part.** The Dockerfile copies `mobile/codex-requirements.toml` to `/etc/codex/requirements.toml`, which turns the `hooks` feature on and points `SessionStart` at `/mobile/pd-codex-session-start`. A user- or project-level hook sits behind interactive trust approval, and a restored tab cannot answer a trust prompt — a hook that silently never runs is a tab that silently comes back blank. `test/server/codex.test.js` asserts the install and the `hooks = true` flag for that reason.

**The hook is inert outside a pocket-dev Codex tab, by having nowhere to write.** Only such a tab is handed `PD_CODEX_SID_FILE` (with `PD_STATE_DIR` beside it, so the hook validates against the same state dir the server uses rather than re-deriving one from `$HOME`); with no destination it exits 0 and touches nothing, which is what an ordinary `codex` run in a shell gets. It accepts only a uuid, and only a destination that is `<state dir>/sids/<SAFE_ID>.uuid`.

**Codex deliberately keeps the shared `CODEX_HOME`.** Splitting the home per tab would also split or duplicate config, credentials, packages, plugins and skills. The explicit uuid makes selection inside one shared home unambiguous without copying any of that. DO NOT replace it with a most-recent selector: two tabs in the same cwd would pick the same conversation. DO NOT parse rollout files or `transcript_path` either — Codex documents the hook's `session_id`, while its transcript format is explicitly unstable and ships its own migration away from itself. The restore-time turn status obeys the same rule from the other side: it comes from a supported App Server method, never from those files.

The load-bearing rule is **first loop iteration resumes, later ones never do**, and both launchers implement it. Iteration 1 means pocket-dev respawned the tab (the restart case, resume the recorded id); iteration 2+ means the provider exited because the user typed `/exit` (a clean slate is the point, and resuming there would trap them in a conversation they cannot leave). DO NOT collapse this to resuming unconditionally. `pd-codex-session` DELETES the sid file before starting fresh rather than merely ignoring it, because a crash between that start and the new `SessionStart` event would otherwise leave the abandoned conversation bound to the tab.

`mobile/pd-codex-bind-current` is the one-time bridge for a Codex tab created before the hook existed. It must run as a tool inside that tab's own Codex conversation, where Codex supplies `CODEX_THREAD_ID`; it derives the tmux tab name, then reads that thread through Codex App Server before feeding a verified resumable id through the same hook writer without printing either id. **DO NOT persist `CODEX_THREAD_ID` directly, and DO NOT assume one `sessionId` jump reaches the TUI root.** A tool running under multi-agent v2 can see its child thread id, and nested subagents can form several session trees: `thread.sessionId` roots the current tree, but that root can itself have `parentThreadId`. The helper therefore follows supported `thread/read` records through `parentThreadId` until it reaches the first thread with no parent, rejecting cycles and excessive depth. A thread that starts with no parent keeps its own id, including a user-facing fork. This is deliberately App Server metadata rather than the unstable rollout JSONL. The managed writer applies the official `SessionStart.source` contract: `startup` is first-writer-wins, `resume` and `compact` cannot displace the established root, and `clear` replaces it because the user intentionally started a new conversation in the same TUI. Live pre-deploy evidence on 2026-09-11 found two long-running tabs whose compact-era events had replaced valid roots with identities absent from both the rollout and state indexes. The hook publishes ordinary events with a no-replace hard link and clear with an atomic rename. Only the migration helper sets `PD_CODEX_REPLACE_BINDING=1`, because its App Server walk has verified the replacement root and its purpose is to repair a stale pre-upgrade target atomically. Every invocation uses a collision-resistant temp name so a file left by a killed container cannot suppress the next root event after PID reuse. Bind immediately before the upgrading recreate: if the old Codex process exits after binding and before deployment, bind its replacement again, because the pre-upgrade generic loop cannot update the file.

**3. The restore continuation prompt (`mobile/claudeSession.js`, `mobile/codexTurnStatus.js`).** A restored session that was mid-turn is asked to carry on; one that was waiting on the user or had already settled is left alone, which is the whole reason to classify rather than always continue. Claude classifies its transcript tail: a completed assistant turn (`stop_reason: 'end_turn'`) or a `[Request interrupted by user` marker is idle, a completed turn ending in a `USER_INPUT_TOOLS` call is `asking`, anything else recognisable is busy, anything unrecognisable is `unknown`. Codex does NOT parse a transcript. `pd-codex-thread-status` calls the supported read-only `thread/turns/list` App Server method with `limit: 1`, descending order, and unloaded items. `interrupted` and `inProgress` are busy; `completed` and `failed` are settled. Missing, malformed, timed-out, or unsupported results are `unknown`. **`unknown` must never prompt** — a wrong "busy" makes a provider talk to itself. **`asking` must never prompt either**, and for a sharper reason: the pending record is a question put to the user, so the prompt arrives as its answer and Claude acts on a choice nobody made. This lookup is restore-only; the session list still reports Codex status as untracked because pocket-dev does not continuously supervise its live turn.

**That read is one bounded batch per restore, and it fails closed in every direction.** `restore()` collects the uuids of every resumable Codex tab and hands them to the injectable `codexTurnStatuses` (defaulting to `readCodexTurnStatuses`) in a SINGLE `pd-codex-thread-status` invocation, so one App Server start covers every tab rather than one per tab, and ONE aggregate deadline bounds the whole boot: `PD_CODEX_STATUS_TIMEOUT_MS` inside the helper (default 10 s) under the server's own fixed 12 s `spawnSync` cap, so raising the knob past that buys nothing. Thread ids travel on stdin, NEVER argv, and the helper's App Server stderr is discarded because an upstream diagnostic can quote the id back; statuses come out one per line in input order, and a position that cannot be resolved is `unknown` rather than shifting its neighbours. An unreadable thread, a malformed reply, a short or long line count, a non-zero exit: all of them land on `unknown`, which restores the tab with no prompt, and a lookup that throws outright also logs a warning.

The prompt travels as `PD_RESUME_PROMPT` (tmux `-e`) and becomes a command-line argument on the launcher's first iteration: `claude --resume <id> "continue please"` or `codex resume <flags> -- <id> "continue please"`. Later loop iterations start fresh and receive no prompt. **The `--` in the Codex form is load-bearing**: the id and the prompt are positional, so without it a prompt that happens to start with a dash is parsed as a flag — `codexSessionLauncher.test.js` pins that with `PD_RESUME_PROMPT=--help`. **DO NOT change this to typing into the pty.** That was the first Claude implementation and it fails live: a resuming Claude paints, pauses while it initialises, then repaints, and anything typed into that gap is swallowed with no error. There is no ready signal to wait for, so no settle timeout fixes it. As an argument it is the provider's own first message, it cannot be lost, and it survives the workspace-trust gate. Verified for Claude 2026-07-24 and for Codex 2026-09-11.

**Auto-continue is gated on a CLEAN shutdown, and that gate is a safety property, not a nicety.** `startServer()` registers SIGTERM/SIGINT handlers that drop a `clean-shutdown` marker in the state dir, and reads-and-clears it at boot. Marker present (a deliberate `docker restart`, stop, or image update) means an interrupted session may be told `continue please`. Marker absent covers every way a process dies without a say — SIGKILL, an OOM kill, the host losing power — and there the session is still restored and its conversation still resumed, but instead of being told to carry on it is WARNED (`PD_CRASH_NUDGE`) that the container died and that retrying may repeat whatever killed it. The reason is concrete: a Claude session can OOM the host by building something the wrong way, and "continue please" after that is an instruction to do it again. Unclean is the default, so knowing nothing gets you the cautious branch. DO NOT invert this to opt-in. The marker distinguishes clean from unclean deterministically; it does NOT identify why an unclean exit happened, and nothing readable from inside the restarted container does.

Resume is off for every provider whenever `SHELL_CMD` is set (the e2e fixture runs `cat`, which has no conversation) or `PD_RESUME=0`, and a session with resume off gets the plain inline loop instead of a launcher. The roster half still works in both cases. Note `claude --resume` is scoped to the cwd's project, which is fine because every session spawns in `$HOME`; `codex resume` takes an explicit id and needs no cwd-based selection. If either resume fails anyway the loop self-heals, because iteration 2 is no longer the first and starts clean.

**4. The trust gate (`mobile/pd-trust-workspace`, called from `start.sh`).** Claude asks "do you trust this folder?" on every new session in an untrusted directory, and measured in the running container, answering it does not persist for `/home/claude`. Restored sessions would therefore all come back parked on a prompt, waiting for a keypress, which defeats restoring them. The script pre-accepts the gate at boot, before any session spawns. It grants nothing new: pocket-dev already runs `--dangerously-skip-permissions` in that exact directory. `PD_TRUST_WORKSPACE=0` opts out. It writes `~/.claude.json` in place with `cat >`, never a rename. That was originally because the path was a file-level bind mount, where a rename fails with EBUSY; the single home mount retired that specific mount, but the in-place write and the inode assertion in `test/server/trustWorkspace.test.js` are kept, because they are what makes re-introducing a file-level mount there safe and the failure is otherwise silent.

**The client half** (`index.html`). Panes reconnect on their own: `term.reset()` on every WS open stops a reconnect stacking a second copy of the scrollback, and the server's replay followed by tmux's authoritative repaint is what rebuilds the pane (the replay alone cannot — see "Terminal replies across reconnects"). A 4404 triggers `resyncSessions()` instead of leaving a dead pane, and coming back to a backgrounded tab resyncs too — that is when a restart is most likely to have happened unseen.

**A pane stops following new output when the BROWSER moves it, and xterm cannot tell that from a user scrolling.** `Viewport._handleScroll` turns any `scrollTop` xterm did not itself set into `scrollLines(newRow - ydisp)`, and a negative result latches `isUserScrolling`, which stops the buffer following forever. Nothing clears that latch on its own.

Measured on webkit in CI after a node-only restart (#30), from a scroll-event trace, not from reading source: xterm syncs `scrollTop` to 32 (`ydisp 2 * 16px`) against a 671px scroll area, then a later viewport refresh shrinks the area to 639px, *exactly* `clientHeight`, leaving no scrollable range at all. The browser clamps `scrollTop` 32 -> 0 by itself. xterm reads that unflagged event as a 2-row scroll up and the pane sits 2 rows off the bottom for good, showing a window that straddles the pre-restart paint and the replayed one. Chromium and Firefox coalesce the clamp with the flagged event, which is the entire reason it read as webkit flake.

`installFollowGuard()` in `index.html` is the fix. It watches the viewport's own scroll events and **discriminates on GEOMETRY, deliberately, not on input devices**: a browser only relocates `scrollTop` on its own when the scroll area shrinks under it, so a scroll arriving with the area unchanged is the user's and is left alone, while one arriving with the area shrunk (or with no scrollable range at all) is undone. `test/e2e/follow-guard.spec.js` is the regression guard; it provokes the clamp by collapsing the scroll area rather than by assigning `scrollTop`, because the geometry change is the whole signal.

Two dead ends are recorded in the code as DO-NOTs, both of which were tried:

- **Do not track wheel/pointer/touch and treat "no gesture" as proof the browser did it.** Dragging a native scrollbar dispatches no `pointerdown` in Chrome or Firefox, so a real drag looks gestureless and the guard fights the user. The viewport has a real scrollbar; it is not styled away.
- **Do not rely on the `term.scrollToBottom()` that follows `reset()` in `ws.onopen`.** It was once believed to be the whole fix and CLAUDE.md said so; the CI trace disproves it. At that point the buffer is empty from `reset()`, so it resolves to `scrollLines(0)`: it clears the latch and moves nothing. Everything that actually unpins the pane happens *after* it. It is kept because a reattach should start following whatever the pane was doing before, not because it fixes this.

**Never assert on a marker count taken across the whole buffer, and never take it from rendered text.** Both were wrong in `restore.spec.js` and cost a day of "webkit flake". The row count is not stable across a reconnect (`fitAndResize()` runs on every WS open), and shrinking a terminal reflows lines that no longer fit into scrollback while growing it pulls them back, so a whole-buffer count taken after a restart is not comparable with one taken before it: measured 2 -> 4 -> 6 across a restart and two resizes. Rendered text additionally reflects wherever the pane happens to be scrolled. The stable measure is the bottom-anchored SCREEN (`buffer.normal` rows `baseY` .. `baseY + rows`), which held steady at 2 through every one of those steps on all three browsers.

**Where the state lives.** `PD_STATE_DIR` defaults to `/home/claude/.pocket-dev`, inside the single `Home` mount — see "The home is one mount" below. Unmounted it would survive a restart but NOT a recreate, because a recreate discards the writable layer.

**Conversation metadata** rides the same transcript read. `claudeSession.inspectTranscript` returns `{status, turnId, title, lastPrompt, archivedId}` from ONE tail pass, because the session list asks for status, title and the archive notice together and repeatedly. Claude appends a fresh `ai-title` and `last-prompt` record on roughly every turn (98 of each in one real 11 MB transcript), so the LAST occurrence is current and we walk backwards to it; measured across six real transcripts both sit within 32 KB of EOF even at 14 MB. `GET /sessions` serves `describe()`, not `list()`: `list()` stays cheap because it is also what gets written to the roster on every create and destroy. `describe()` memoises per uuid against the transcript's mtime and size, which is sound because a transcript only ever grows.

**Test coverage** splits along the same seams: `test/e2e/restore.spec.js` drives real restarts through the browser (roster half only, since the fixture is `cat`); `test/server/sessionsRestore.test.js` injects a fake pty to cover restore, id sequencing, which launcher and which env each provider gets, and every branch of the Claude and Codex resume decisions; `test/server/sessionLauncher.test.js` and `test/server/codexSessionLauncher.test.js` run both launchers against stubs on PATH (the Codex one also pins that two restored tabs cannot converge on one conversation and that only the first iteration gets a prompt); `test/server/codexSessionHook.test.js` drives the exact hook input contract, including the destinations and sources it must refuse, compact preserving the root, clear atomically rebinding, no stranded invocation temp, and a stale PID temp not suppressing the next root event; `test/server/codexMigration.test.js` covers the pre-upgrade bridge against a stub `codex app-server` on PATH, including the nested-subagent parent walk, a root and a no-parent fork staying bound to themselves, the atomic replacement of a stale binding with the verified root, and the cycle and App Server error cases failing closed without printing any thread id; `test/server/codexThreadStatus.test.js` covers the newest-turn request and every supported, missing, malformed, error, timeout, and invalid-id result without exposing a thread id, plus the batch cases (input order preserved, one bad position isolated, one aggregate deadline); `test/server/claudeSession.test.js` pins the Claude transcript shapes the classifier reads; `test/server/trustWorkspace.test.js` runs the trust script for real; and `test/e2e/titles.spec.js` runs on the `pdServerClaudeStub` fixture, which leaves `SHELL_CMD` unset and shadows `claude` on PATH with `test/e2e/stub-bin/claude` so the launcher, the sid-file handoff, and titles all execute for real in a browser test. That stub derives its log path from `PD_SID_FILE` rather than its own env var, because tmux only forwards what `update-environment` names and a pty-set variable arrives only when that test happened to start the tmux server: it passed alone and failed under parallel workers. None of that substitutes for a live pass against EACH real provider: resume is exactly the kind of path that is green against a stub and broken against the actual CLI, which is how the typed-nudge design got caught.

## The session list — four states from two sources

`#session-list` is a full-screen overlay (NOT a swap of `#terminal-stack`'s contents: the panes underneath must keep their layout, see the `.terminal-pane` comment). It is opened by the `Sessions` button, and each row is a session with its conversation title, a preview line, and one of four states. The model itself lives in `mobile/public/js/attention.js` — pure, unit-tested, and the single place that decides what "needs me" means.

**Three of the four states come from the transcript; the fourth cannot.** `classifyTranscript` returns `busy`, `idle`, or `asking`. But **"waiting on you" and "read" are the SAME `idle` transcript state** — nothing on disk knows whether a human has looked. DO NOT go hunting for that distinction in the JSONL; it isn't there.

| Row state | Source | Wants the user? |
|---|---|---|
| `asking` | transcript: a pending tool call only a human can answer | YES, and it does not clear when looked at |
| `working` | transcript: `busy` | **NO** |
| `waiting` | `idle` + server says unread | YES |
| `read` | `idle` + server says read | no |

**`working` is deliberately NOT attention, and that is the point of the table.** The rule used to be "anything not `read` wants you", so the badge fired for every thinking session — and something is almost always thinking, so it was on permanently and answered nothing. Reported 2026-07-27: "I find myself still frequently going into the sessions tab to see what needs my attention." The `Sessions` button therefore has TWO tiers, `data-badge="attention"` (green, act) and `data-badge="working"` (dim amber, nothing to do), and `#sessions-btn.has-unread` is gone.

**`asking` is what a pending question looks like from outside, and the tool NAME is the only thing that reveals it.** A completed assistant turn ending in a tool call is identical whether the result comes from a machine or a person; `USER_INPUT_TOOLS` in `claudeSession.js` (`AskUserQuestion`, `ExitPlanMode`) is the discriminator. Measured on the live container 2026-07-27: a session sat on an unanswered `AskUserQuestion` for 39 minutes, reported as "Working" throughout. Gated on `stop_reason === 'tool_use'`, because an interrupted stream can carry a half-written call that never ran. DO NOT widen this to pendingness in general or every `Bash` call becomes a summons. `asking` also never gets a resume prompt at restore: "continue please" would arrive AS the answer to the question.

**The unread axis counts TURNS, not bytes**, and is server-side so every device agrees (read it on the phone, it is read on the desktop). `state.attentionSeq` against `state.viewedSeq`, with `POST /viewed` catching the latter up. `noteTurn` advances it when a session's `{status, turnId}` changes into a status in `WANTS_USER`, where `turnId` is the deciding transcript record's own uuid. Three things follow, all of them the reason it is shaped this way:

- **A repaint cannot make a session unread.** Bytes were the first unit and were wrong: a TUI coder emits a frame per thought, so every thought re-flagged the session. It also meant a session that had merely redrawn reverted to wanting you, with nothing to explain why.
- **Comparing the turn, not just the status, closes the poll gap.** Two consecutive finished turns both read `idle`; only the record uuid separates them, so a turn that starts and finishes between two polls is not lost.
- **Bookkeeping records cannot move it.** `ai-title` / `last-prompt` are appended between turns but are not message records, so they never become the deciding one.

Counting still falls back to raw pty output for a session whose status is `unknown` — no transcript yet, or a custom `SHELL_CMD` that is not Claude — because there, output is the only evidence that exists. That is why `unknown` is NOT in `WANTS_USER` (becoming unclassifiable is not news) yet an `unknown` session can still be unread: it has a second news mechanism the others do not. `test/unit/statusContract.test.js` pins that asymmetry, along with the fact that the browser handles every status the server can emit — the two vocabularies cannot import each other across the wire, so a test is what stops them drifting. Wall-clock timestamps were an earlier implementation and were wrong at a lower level: something landing in the same millisecond as a view compares equal and gets swallowed, and no choice of `>` or `>=` fixes it. `lastOutputAt` survives only as a display value for the row's relative time.

Both counters restart with the process, and `create()` **seeds** `status`/`turnId` from the transcript so the first look after a restart is not mistaken for a fresh turn. That is the whole mechanism; DO NOT add a "skip the first observation" guard on top of it (a null-`turnId` version of that suppressed every transition in a transcript whose records carry no uuid). A session holding a question still surfaces after a restart, because `asking` does not travel on the unread axis at all.

Three rules the UI depends on. **The active session is never unread** (you are looking at it, so its output is read as it arrives). While you sit in a session a throttled `POST /viewed` keeps the server's record in step so another device does not still think it wants you, and leaving a session **flushes** it unthrottled, because the throttle otherwise leaves whatever it printed in the last two seconds permanently unacknowledged. And `markViewed` **observes the transcript before catching the counter up**, so a turn that finished since the last poll is counted as read rather than announced afterwards — that ordering is load-bearing and tested.

**Arriving bytes never mark a session unread in the BROWSER.** The client cannot tell a finished turn from a repaint, and the server replays its whole buffer on every WS attach, so an optimistic client-side flag meant every reconnect — a phone waking, a network blip, a restart — claimed that every session the user was not looking at wanted them. The badge is worth one poll interval of latency instead, which is why `pollDelay` tightens to 4s while another session is `busy` or `unknown` and relaxes to 8s when nothing can change. `test/e2e/session-list.spec.js` guards this on the BACKGROUND session specifically, with the metadata poll stalled so the client cannot quietly correct itself: asserting on the active session proves nothing, since the active session is never unread by definition.

The list REPLACED the cycle row: `#btn-row-tmux` and its Next/Last buttons are gone, `Kill` moved into the session's own toolbar next to the thing it destroys, and `#session-label` became a permanent strip above the toolbar (outside `#btn-group`, so collapsing the toolbar cannot hide it — on a phone there is no browser tab title, so it is the only persistent answer to "which session am I in"). Cycling survives only as the Ctrl-B prefix keys, which need no UI.

## Remote Control — the other way into a session

`DEFAULT_CMD` carries `--rc`, so every tab registers with the Remote Control bridge and can also be driven from claude.ai/code or the Claude mobile app. The browser terminal and Remote Control are two views of the same tmux session, not alternatives, and a phone is exactly where the second one earns its keep.

**It has to be the flag, and this is the part that will get "simplified" one day.** Claude Code ships a documented user setting, `remoteControlAtStartup`, whose description is "Start Remote Control bridge automatically each session". Measured 2026-08-02 against 2.1.220, it does not do that. Setting it true in `~/.claude/settings.json` and launching three ways (a bare `claude`, one through this server, and one with the same key injected via `--settings`) produced no bridge in any of them, over several minutes each, while `--rc` produced one every time. The resolver in the binary genuinely reads user settings, so this is not a placement mistake; the value is read and then nothing acts on it. Swapping the flag for the setting therefore reads as a tidy-up and silently turns Remote Control off. `sessionsRestore.test.js` guards the flag for the same reason `tmuxConf.test.js` guards its knob: the bridge needs a real account and a round trip to claude.ai, so the cat-based e2e suite cannot see any of this.

Two smaller traps in the same line:

- **`-rc` with one dash is not an abbreviation of `--rc`.** Commander splits it into `-r c`, which is `--resume c`, and the session comes up looking for a conversation named `c`.
- **`--rc` takes an OPTIONAL name, so it must never be the last token.** `pd-claude-session` appends `--resume <uuid>` or `--session-id <uuid>`, and a trailing `--rc` would consume the first of those as its session name. Keeping `--remote-control-session-name-prefix` immediately after it makes that structural rather than a thing to remember.

`PD_REMOTE_CONTROL=0` turns the whole thing off, the same shape as `PD_RESUME` and `PD_TRUST_WORKSPACE`. A bridged tab is drivable by anyone holding the account, and the flag lives in the image, so the alternative to a knob is rebuilding to get out of it.

The prefix is there because an auto-generated name is `<hostname>-<random words>` and this container's hostname is a docker id that changes on every recreate, so the phone would otherwise list tabs as `d969bbd91655-mossy-frog` and rename them all on the next image update.

**Claude's own conversation title does NOT reach the phone on its own, so the server types it in.** The binary contains the machinery (an `updateBridgeSessionTitle` call, and a name-resolution order preferring a custom title, then the `ai-title`, then the last user message, then the random name), but driving a real session through a turn produced an `ai-title` and no rename. `/rename` DOES reach the bridge, verified in its log, because it writes a `custom-title`, which outranks everything else and locks the name against later auto-titling.

The name is resolved at REGISTRATION and never revisited, and that is what scopes the fix. A resumed conversation already has an `ai-title` on disk to register under, so it names itself correctly and the server leaves it alone. Only a tab opened before its conversation existed gets the random name and keeps it, so `maybeAutoName` in `server.js` waits for that tab's first title and types `/rename <title>` at it once.

**Typing into the pty is the only channel, and that is why the guards look paranoid.** `claudeSession.js` is inspection-only and pocket-dev does not write into `~/.claude/projects`, so appending the record directly is not an option. A write therefore lands in whatever the user is composing, and the rename is cosmetic while a half-written message is not. So it fires only for a session that had no title when it was adopted (which is what confines it to new tabs, and what stops a long conversation being renamed out from under a name chosen on the phone), never while the status is `busy`, and never within `AUTO_NAME_QUIET_MS` of the last keystroke. `autoNamed` is set before the write, so a failure cannot retry forever. The command and its newline go as ONE write: measured 2026-08-02, the slash-command palette opens on `/` but does not swallow the trailing carriage return.

`PD_AUTO_NAME=0` turns just this off, separately from `PD_REMOTE_CONTROL`, because bridging a session and typing into it on the user's behalf are different amounts of trust.

**Archiving a conversation somewhere else closes its tab here.** Archive from the desktop app, the phone, or claude.ai/code and the bridge closes 4090, but the Claude process does not exit, so the tab used to sit in the strip forever holding a conversation its owner had already finished with. Measured on the live container 2026-09-03: 6 of 11 open tabs were in exactly that state.

**The signal is already on disk, and it must be matched as a RECORD.** Claude Code appends this to the conversation's own transcript, which is the file `claudeSession.js` already tails every poll, so `findArchivedNotice` needs no watcher and no pty scraping:

```json
{"type":"system","subtype":"informational","level":"warning",
 "content":"Remote Control disconnected — this session was ended or archived from another device or app (code 4090)","uuid":"..."}
```

DO NOT reduce this to a `line.includes(...)` scan of the tail, and DO NOT key it on `(code 4090)`. Both are measured wrong:

- **A `type:"user"` record carries the sentence verbatim whenever anyone quotes it.** The request that built this feature pasted the message into a prompt and a shell probe printed it into a tool result, so both shapes are on disk in Jake's own transcripts. A phrase scan closes a live tab on either. Requiring `system` / `informational` is the whole discriminator, and `test/server/claudeSession.test.js` pins it with fixtures that carry uuids — without a uuid they get rejected for the wrong reason and the case passes with the check deleted.
- **Three other reasons share code 4090** and none of them means a human is done: `superseded_by_worker` ("is standing down", the conversation is alive elsewhere), `session_not_found` ("may have been deleted", which reads the same as the server losing the registration), and `epoch_stale`. A `Remote Control disconnected — /login` notice is the same record shape again and only means the account signed out. All of these were present in the same sample of 30.

**The seed is the mechanism, exactly as it is for the unread axis.** `create()` records the notice the conversation already carried when the tab was adopted, and only a DIFFERENT one fires a close. That is not defensive tidiness: of 23 real archive events, 19 were the last thing that ever happened in the conversation but **4 were followed by more work** (at +1.3 min, +21 min, +129 min and +16 h), two of them by roughly 1450 further turns. The notice stays in the tail window while a conversation carries on, so without the comparison every container restart would close exactly those tabs, and would do it again on the next restart.

**What a close actually costs is the tmux pane, NOT the conversation.** This is easy to overstate and was overstated while the feature was being designed. Nothing here writes to `~/.claude/projects`; archiving is a state on the CLOUD side of the bridge (every `archived` branch in the binary reads `worker_status` or `environment_kind`, never the local transcript); and the transcript is what `claude --resume` lists. So a wrongly closed tab costs its scrollback and one trip through the resume picker. Jake chose the outright close over a recoverable one on 2026-09-03 knowing the 4-in-23 figure, and that resume path is why it is a cheap bet. DO NOT soften it into a grace period on the strength of the same numbers: a delay cannot save the +129 min and +16 h cases, so it buys far less than it appears to while stopping the feature doing what it was asked for.

**It only ever closes a session whose status is in `TURN_SETTLED`, and that gate is POSITIVE on purpose.** Killing tmux mid-turn destroys work in flight with nothing recording that it ever ran. `status !== 'busy'` reads as the same test and is not, because it lets `unknown` through, and `unknown` is what `decide()` answers when the tail holds no complete message record: one way to get there is a single `tool_result` larger than `TAIL_BYTES`, which happens exactly while a session is mid-tool-call. DO NOT simplify the set back into a negation. `test/unit/statusContract.test.js` pins it, and `TURN_SETTLED` is a separate constant from `WANTS_USER` even though they are identical today, because "a human needs to see this" and "nothing is running" are different questions that a fifth status could answer differently.

**The notice is latched the moment it is seen, BEFORE the settled check, and that is not tidiness.** `findArchivedNotice` only reads the last `TAIL_BYTES` of the transcript, so a notice that arrives mid-turn gets pushed out of the window by the rest of that turn's output and is then gone for good. Deferring on the status alone loses the event outright and silently: the tab simply never closes and nothing says why. `state.archivePending` holds it until the turn settles, and is memory-only so a restart forgets it and the seed takes over.

The same window bounds what an unpolled archive can do: if nothing polls until a lot of work has followed the notice, the event is missed and the tab stays. That direction is fail-safe, which is why the window is not chased with an incremental-offset reader.

Like `maybeAutoName`, it rides the metadata poll rather than a timer, and is bounded the same way — nothing polling means nothing closed. That is the right trade here too: the user archives from somewhere else, so nobody is watching pocket-dev at that moment, and what they want is the tab gone the next time they look, which is by definition a moment the browser is open and polling.

`PD_ARCHIVE_CLOSE=0` turns just this off. It also depends on `RESUME_ENABLED` for its DATA rather than as a preference: without conversation tracking `observe()` answers `NO_META`, so there is no transcript to read.

**Every deliberate removal now closes the session's websockets with `GONE_CODE` (4404)**, the code the browser already reads as "stop reconnecting and re-read the roster". Closing them with no code told the client the opposite of the truth, so a tab killed from another device (or closed by this feature, or whose tmux session was killed by hand) left a dead pane on screen for the two seconds it took to earn a 4404 the long way round. The number crosses a wire and so is written twice; `statusContract.test.js` ties the server's exported constant to `index.html`'s `ws.onclose`, because moving the constant and its own test together is otherwise a green change that breaks every client.

**`killSession` is injected into `createSessionsApi`, and the reason is that its default is destructive to things the tests do not own.** `SESSION_BASE` falls back to `main` when `TMUX_SESSION` is unset OR EMPTY, and pocket-dev's own container sets it empty, so `api.destroy('main-1')` in a server test ran a real `tmux kill-session -t main-1` against the developer's live tmux server. Killing a session that happens not to exist is indistinguishable from killing one that does, so nothing ever reported it. Every `createSessionsApi` in `sessionsRestore.test.js` now passes a recording fake, and a source-level guard in that file asserts the next construction site does too. It also made the kill assertable at all: before, every test passed with the `tmux kill-session` deleted. A failed kill is now logged, because by then the roster entry and the conversation id are already gone, so the tmux session is orphaned with Claude still running in it.

**Test coverage** runs on the `pdServerClaudeStub` fixture rather than the `cat` one, for the reason `titles.spec.js` does: `SHELL_CMD` switches the whole conversation machinery off, so on the cat fixture this feature is not merely untested, it is disabled. `test/server/sessionsRestore.test.js` covers the seed, the settled gate, the latch and the knob; `test/e2e/archive-close.spec.js` proves the BROWSER lets the pane go (including the close code, which the other cases pass without); `test/e2e/archive-close-artifact.spec.js` is an on-demand screenshot run (`PD_ARTIFACTS=1`, chromium only), not a guard. The exact notice bytes live in ONE place, `test/fixtures/rc-notices.js`, shared by all of them and deliberately NOT derived from `claudeSession.js`'s matcher constants: defining both from one source would make every assertion agree with the matcher by construction. None of it substitutes for the live pass in `MANUAL-VERIFICATION.md` — a real archive from another app is not reachable from CI.

## The home is one mount — and why that was ever hard

`/home/claude` is a single bind mount, and the only state mount the container has. Everything written to `~` persists across an image update: Claude's config and conversation ids, the `gh` token, the dgvpn registration, `~/bin`, and credentials for tools no one has added to a list (`.aws`, `.kube`, `.fly`, `.docker`).

**It was not always safe to do this, and the reason still constrains the design.** The home used to hold image artifacts and state in the same directory: `claude`, `uv` and `uvx` in `.local/bin`, the shell rc files, `.config/fish`, `.config/uv`. A mount over the home masked all of it and produced a container with no Claude in it, which is why the old template carried one mount per dotfile, and why the Dockerfile still says DO NOT mount `.local`. That list was the actual bug: anything it forgot — `~/.aws`, `~/.kube`, an installed flyctl — vanished on every recreate, and looked fine until it did.

The separation is what makes the single mount work, and all three pieces are load-bearing:

1. **The image builds its home into `/opt/pd-home`** and leaves `/home/claude` empty (`mv` at the end of the Dockerfile). Nothing image-owned may be created at `/home/claude/...` in the image — the mount masks it.
2. **Absolute symlinks are rewritten into the skeleton.** The claude installer writes `.local/bin/claude -> /home/claude/.local/share/claude/versions/<v>`, an ABSOLUTE path, so a bare `mv` leaves a link that resolves only once `entrypoint.sh` has linked `~/.local` back. That circular dependency means a container whose seeding failed has no runnable Claude and no obvious cause. `PATH` points at `/opt/pd-home/.local/bin` directly for the same reason. DO NOT drop the rewrite and lean on the seeding.
3. **`entrypoint.sh` symlinks the image-owned entries back into `$HOME`** at boot: `.bashrc`, `.zshrc`, `.profile`, `.bash_logout`, `.local`, and the two leaves `.config/fish` and `.config/uv`. **Links, never copies** — a copy freezes at first boot, so an image update would ship a `claude` no container runs. Only the leaves of `.config` are linked, because `.config/gh` holds the auth token and must persist.

Two rules that follow:

- **Session-installed CLIs go in `~/bin`** (on `PATH`, inside the mount). NOT `~/.local/bin`, which is a symlink into the image skeleton where writes are lost on the next update. This replaced `/opt/pd`, which existed only because the home was not persistent and was never actually mounted on the live container anyway.
- **`~/.cache` and `~/.npm` are relinked to `/var/tmp/pd-cache` and deliberately NOT persisted.** The home mount lands on the UnRAID array over shfs FUSE; a large write-heavy cache is the wrong traffic for it and pure bloat in appdata backups.
- **`~/.codex/tmp` is relinked into the same container-local cache, mode 700, and that one is a correctness fix rather than a traffic one.** Codex 0.153.4 removes its arg0 helper directories while still holding their `.lock` files open. On shfs, unlinking an open file leaves a `.fuse_hidden*` entry behind, so the `rmdir` fails with `Directory not empty (os error 39)` and every startup strands another helper directory in the persisted home. Measured 2026-09-09: the identical open-lock-then-remove probe fails on the home mount and succeeds under `/var/tmp`. Relocate ONLY the process-lifetime helpers — never `auth.json`, `sessions/`, `packages/` or `config.toml`, which are the state the single home mount exists to keep. The relink happens in `entrypoint.sh` before the remote-control daemon or any session starts, and DO NOT run that migration against live Codex processes: their `PATH` points at helper directories underneath it.

Guard tests: `mobile/test/server/entrypointSeed.test.js` executes the seeding block for real against a temp home — it asserts `~/.codex/tmp` ends up a symlink to a mode 700 directory in the cache, that a stale `tmp/arg0` tree left by an earlier boot is gone, that `auth.json` and `sessions/` come through untouched, and that a second boot with the cache discarded (the recreate case, where the home keeps the symlink but its target is gone) re-creates the target rather than leaving a dangling link. `mobile/test/server/homeMount.test.js` covers all three files (Dockerfile, `entrypoint.sh`, `pocket-dev.xml`), including an assertion that the template declares **no** mount at a path underneath `/home/claude`. A second mount under the home shadows part of it and lands state in two places at once. Every failure mode in this area is quiet — a container that boots fine with no `claude` on `PATH`, or a home that looks persistent until the update eats it — and none of it is reachable from the cat-based E2E suite, so source-level guards are the whole safety net.

- The package manager is **pnpm**, pinned by `packageManager` in `mobile/package.json` and read from that one place by both corepack (in the Dockerfile) and `pnpm/action-setup` (via `package_json_file` in CI). Do not repeat the version anywhere else.

The load-bearing key is **`allowBuilds`**: pnpm blocks dependency build scripts by default and node-pty ships no linux-x64 prebuild, so without it every server suite fails with "Cannot find module ./prebuilds/linux-x64//pty.node". `onlyBuiltDependencies` is pnpm 10's spelling and 11.17.0 ignores it silently — the file records the measurement.

## Deepgram tailnet access (dgvpn)

`dgvpn` gives commands selective, opt-in access to Deepgram-internal services (`.consul`, request-raid, anything on the `controlplane.deepgram.com` tailnet) without putting the whole container on the VPN. It exists so the in-container Claude can reach those services on its own:

```
dgvpn curl http://request-raid.service.awsw2.consul:9008/health   # routed via tailnet
dgvpn gh repo view ...                                            # public egress, untouched
```

- **`dgvpn <cmd>`** runs `<cmd>` with `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` pointed at the local proxy, then execs. Only hosts matching a tailnet suffix (`.consul` by default, `DGVPN_TAILNET_SUFFIXES` to extend) take the tunnel; everything else dials direct, so `dgvpn` is safe to prefix on any command.
- **`dgvpn-up`** brings the tunnel up (idempotent). Auth is interactive Keycloak SSO, valid ~24h: on first use in a window it prints a login URL to open once. `dgvpn` calls `dgvpn-up` for you and exits with code 3 (not running the command) when login is pending, so the caller authenticates and retries.
- State lives under `/home/claude/.dgvpn`. That survives a restart on its own, but survives a container RECREATE only if the `dgvpn State` volume from `pocket-dev.xml` is actually mounted on the running container. Verify with `docker inspect pocket-dev` before claiming a recreate keeps the registration: the template declaring a volume is not the same as the container having it.

**Architecture lives in `vpn/`.** A static Go binary (`dgvpn-proxy`) holds one userspace `tsnet` identity and runs a localhost HTTP CONNECT/forward proxy. `main.go` is the single-identity lifecycle (tsnet up, `RouteAll=true`, surface the SSO URL, start proxy); `proxy.go` is lifted from deephive's `services/tsnet/proxy.go`. It runs as the unprivileged `claude` user: userspace tsnet needs no TUN device and no `NET_ADMIN`. Go tests: `cd vpn && go test ./...`.

**DO NOT replace the Go sidecar with `tailscale up` / `tailscaled`.** This is the load-bearing reason the code exists. Userspace `tailscaled` cannot resolve `.consul` split-DNS for outbound connections (tailscale#16906, tailscale#4677): it answers only globally-resolvable or MagicDNS names, and `.consul` is neither. The sidecar works around this exactly as deephive did (#380), resolving names itself via the tsnet LocalAPI (`proxy.go`'s `resolveViaLocalAPI`) before dialing. Kernel-mode `tailscaled` would also need a TUN device and `NET_ADMIN`, which this unprivileged container does not have. If you "simplify" this to a stock tailscale client, `.consul` silently stops resolving.

## Codex, the second model in the container

`/usr/local/bin/codex` is OpenAI's coding CLI, installed by `npm install -g @openai/codex` in the Dockerfile. It exists for one reason: the `/second-opinion` skill, which consults a different lab's model on a diff or a design call and then adjudicates the two views against the code. The value there is decorrelated error, and a container holding only Anthropic's model cannot produce any. The skill checks `command -v codex` and stops when it is missing rather than quietly substituting Claude's own view, so "the skill is installed" and "the skill can run" are separate facts and the second one is this section.

**It goes in `/usr/local`, and both alternatives are traps.** `/home/claude` is a bind mount that ships EMPTY, so an image-owned binary written under it is masked the moment the mount lands. `~/bin` is worse: it is the prefix for CLIs a SESSION installs for itself, it sits EARLIER on `PATH` than `/usr/local/bin`, and a copy left there would shadow the image's own on every future update, silently, forever. `test/server/codex.test.js` guards both, plus the build-cache ordering (the install is ~300 MB of Rust binary and belongs above `COPY mobile/`, not below it).

**Unpinned on purpose**, the same call already made for `claude` and `gh`, so the tool tracks upstream instead of freezing at whatever was newest the day the line was written. `codex --version` at the end of the build puts the resolved version in the build log, so a build is self-documenting about what it shipped. The `/second-opinion` skill records CLI traps measured against a specific version and says to re-verify after a major bump, which is a per-major job, not a per-build one.

**UNPINNED IS NOT THE SAME AS UP TO DATE, and believing otherwise is what let the version rot.** `cache-from: type=gha` in `docker-publish.yml` derives this RUN's cache key from the instruction and the layers above it, NOT from what `npm install -g @openai/codex` would resolve today, so an unchanged Dockerfile makes it a cache HIT and the version does not move. Measured: the running container sat on codex 0.153.0 while upstream was on 0.153.4. Two things make the claim true and BOTH are needed:

1. **A weekly `schedule:` build** (Monday 06:00 UTC) in `docker-publish.yml` that passes `no-cache: ${{ github.event_name == 'schedule' }}` — cache-busting ONLY that event, because push and PR builds still want the cache for the native node-pty compile. A scheduled build that kept the cache would be decorative: same key, same hit, same codex.
2. **`pocket-dev-codex-update`**, a Tower user script that runs `npm install -g @openai/codex` as root INSIDE the running container. That step exists because a new image on GHCR is not a new codex in the tab: taking it the normal way means a recreate, which ends every tmux session. The scheduled build is deliberately NOT paired with an automatic deploy for the same reason.

**Claude needs neither, and the asymmetry is about where the binary lands.** `install.sh` puts `claude` in a uid-99-writable prefix with its own updater, so it self-updates at runtime. This `npm install -g` lands in root-owned `/usr/local` while the container runs as uid 99, so codex cannot update itself in place — hence the root-run script.

**Auth lives in `~/.codex/auth.json`, inside the home mount, so it survives image updates on its own.** There is no browser in the container, so the login is the device-code flow:

```sh
codex login --device-auth
```

Copying an `auth.json` in from a machine that has a browser also works and is documented upstream, and it is how the container was first authenticated (2026-08-15, `auth_mode: chatgpt`). Prefer the device flow when re-authenticating: the copy puts two machines on one session, and a refresh from either is a shared fate. Verified at the time of the copy that a desktop `codex` and the container's kept working simultaneously, so this is a preference, not a known break. DO NOT put an `OPENAI_API_KEY` in the template to work around a login: the account is a ChatGPT subscription, so an API key would silently move the consult onto per-token billing.

**`entrypoint.sh` creates `~/.codex` and never writes its `config.toml`, and the second half is the deliberate one.** The directory lives under `/home/claude`, which is a bind mount that ships EMPTY, so a Dockerfile `mkdir` there is masked the moment the mount lands — hence the `mkdir -p "$HOME/.codex"` beside the other state dirs in `entrypoint.sh`. What it does put inside is deliberately narrow, and both entries are things a build-time write cannot deliver: the `tmp` symlink out onto the container-local cache (see "The home is one mount"), and the standalone binary under `~/.codex/packages` that `codex remote-control` insists on. Credentials (`auth.json`), conversations (`sessions/`) and the config stay exactly as `codex login` and the user leave them. An earlier version of that block also SEEDED `~/.codex/config.toml` with `model = "gpt-5.6-sol"` and `model_reasoning_effort = "high"` to match cachyos-desktop. It has been removed, for two reasons that both stand on their own:

- **It bought nothing here.** The dominant codex consumer in this container is `/second-opinion`, which pins `-m` and passes `-c model_reasoning_effort` on every single invocation, so a base pin is redundant for the path that matters. Interactive codex is no longer rare — a tab can be started on the Codex provider — but that tab pins its own model on its own command line (see below), so it does not need the base config either. The desktop is the opposite case — `codex` typed daily into a bare shell — which is why the pin is correct THERE and pointless in this file.
- **`~/.codex/config.toml` carries a DO-NOT that forbids it.** That file is the BASE that `~/.codex/deepgram.config.toml` layers on top of, and its own header says "DO NOT set model_provider, auth_mode, or a model here." The Deepgram-billed path is entered only via the `codex-dg` wrapper, and keeping the base minimal is what makes that split reasonable about.

The seed was guarded `if [ ! -e ]`, so on Jake's existing home it correctly did nothing — the defect was latent and would only ever have fired on a fresh home. DO NOT re-add it: set codex options on the command line, or edit the config by hand where the DO-NOT has been reconsidered.

**The image DOES ship one Codex config, and it is deliberately not in the home: `/etc/codex/requirements.toml`.** The Dockerfile copies `mobile/codex-requirements.toml` there to turn the `hooks` feature on and install `pd-codex-session-start` as a managed `SessionStart` hook, which is what binds a Codex tab to its own conversation across a restart — the reasoning is under "Session restore". The managed layer is the point rather than a detail: a user- or project-level hook waits on interactive trust, which a restored tab cannot answer, and writing it there would also breach the rule above that this image leaves the home's config alone. It changes policy for nothing else — `test/server/codex.test.js` asserts the image ships neither `dangerously-bypass-hook-trust` nor `allow_managed_hooks_only`, so the user's own Codex hooks keep whatever trust behaviour they had.

**The standalone install that remote control requires is fetched at boot, and `CODEX_INSTALL_DIR` belongs on the INSTALLER, not on `curl`.** `CODEX_INSTALL_DIR=... curl -fsSL ... | sh` exports the variable for the download only; the installer shell in the second stage of the pipe never sees it and falls back to its own default `~/.local/bin`, which here is a symlink into the image skeleton, so the launcher lands in the container layer and is gone on the next recreate. `~/bin` — inside the mount — is where it has to go, so the assignment sits on the `sh` that reads the script. The pipeline also runs inside a subshell with `set -o pipefail`, because without it a failed download pipes an EMPTY script into a shell that exits 0, and boot logs "installed the standalone codex" for an install that never happened. `mobile/test/server/entrypointSeed.test.js` pins both halves by executing the block: a stub `curl` serving a stub installer that exits non-zero unless `CODEX_INSTALL_DIR` is `$HOME/bin` (and unless `~/.codex/tmp` is already a symlink, since the relink must precede it), and a stub `curl` that just fails, which must still boot the terminal while reporting the failure on stderr.

**There are two Codex provider routes because credential identity changes capability.** **Codex DG** runs `codex-dg --dangerously-bypass-approvals-and-sandbox -m gpt-5.6-sol`; it uses the Deepgram API account and retains the explicit Sol pin. **Codex GPT** runs bare `codex --dangerously-bypass-approvals-and-sandbox`; it uses the persisted ChatGPT login and its connected apps, and deliberately inherits that account's model default. Both use the same `pd-codex-session` resume launcher (which on the first iteration after a restart turns the command into `resume <flags> -- <uuid>`, plus the continuation prompt when restore decided the turn was active), but they remain separate provider ids in the roster so a restart cannot silently change account or billing route. Installing an OpenAI plugin locally is not sufficient for apps such as Slack and Notion: the underlying app must also be connected on the ChatGPT account.

**Composer submission follows the effective command's keyboard protocol.** Claude and a custom `SHELL_CMD` accept carriage return; Codex 0.154 enables Kitty keyboard enhancement and expects Enter as `CSI 13 u`. Codex also classifies a whole composer payload as a paste burst, so `/send` waits 100 ms before Enter and serializes sends per session; without both, Enter is ignored or two requests merge into one prompt. The standalone `enter` key endpoint has no preceding paste and stays immediate. A hard-coded `\r` paints the prompt into Codex's composer but never starts the turn, which looks like a hung app connection even though the text arrived intact.

**The model picker is not proof of which credential serves inference.** Measured 2026-09-09 on 0.153.4: an API tab had the correct key and successfully used Sol, but the shared `models_cache.json` supplied the personal account's shorter catalog. The API profile now sets `cli_auth_credentials_store = "ephemeral"`, so saved personal OAuth credentials cannot make that cache an exclusive ChatGPT catalog. The live picker then showed Astra, Sol, Terra, Luna, GPT-5.5, and GPT-5.2. This profile is owned by the `~/.claude` repo's `codex-dg/install.sh`, not this image. Run `codex-dg-selftest` after profile changes and verify an actual API request, rather than inferring billing or access from a startup banner.

**Before bumping that pin, re-read `~/.claude/skills/second-opinion/SKILL.md` `<model_choice>`** for the must-fail-control recipe, and DO NOT accept the startup banner as evidence: it ECHOES any `-m` string without validating it, so `-m sol` and `-m gpt-sol` both print a plausible banner and neither is a model. The banner is still worth having — it names the model in the one place a tab's user is already looking, which is where a silent downgrade would show — but it confirms what was passed, not that what was passed exists. `test/server/providers.test.js` pins the flag.

**The guard test asserts `entrypoint.sh` does not write that FILE, not that it lacks that SETTING**, and the difference is measured rather than stylistic. The first version matched `/model\s*=\s*"gpt-5\.6/` and the negative control slipped straight past it, because a seed written inside a shell `printf` spells the quotes escaped (`model = \"gpt-5.6-sol\"`). One spelling of one setting is the wrong invariant; `.codex/config.toml` never appearing is the right one and cannot be spelled around. Like the wrapper guard below it, the test strips comment lines first — `entrypoint.sh` NAMES the removed setting while explaining its absence.

**The sandbox flag is not decoration, and `bubblewrap` is in the apt list because of it.** `/second-opinion` always passes `-s read-only`, which on Linux is implemented with bubblewrap. It works unprivileged in this container, verified live 2026-08-15 as uid 99:100 with `sandbox: read-only` in the banner. Codex bundles its own `bwrap` and falls back to it when the OS has none, so the sandbox worked before the package was added too, but every run printed `could not find bubblewrap on PATH`, which reads exactly like the sandbox failing to engage. The package costs ~150 KB and buys a clean banner. DO NOT drop `-s read-only` to make something work: a consultant that can write makes its opinion indistinguishable from its changes, and the diff under review stops being the diff under review.

**There is DELIBERATELY no `codex` wrapper in this image, and that absence is the load-bearing half of the defaults.** Measured 2026-09-07 on codex-cli 0.151.0: `--dangerously-bypass-approvals-and-sandbox` OUTRANKS an explicit `-s read-only`. So a wrapper carrying that flag would hand every `/second-opinion` consult full disk access while the consult still asked for read-only, and the only place it would show is the `sandbox:` line of codex's own banner — a place nobody reads once the answer arrives. pocket-dev is where those consults run. Jake's desktop wraps `codex` with the bypass because it is an interactive daily driver; this container must not, and `test/server/codex.test.js` asserts neither the Dockerfile nor `entrypoint.sh` ships one. That test strips comment lines before matching, because both files EXPLAIN this invariant in prose and a whole-file scan flags the comment describing the absence.

**Codex refuses to run outside a git repo**, with `Not inside a trusted directory and --skip-git-repo-check was not specified`. That is upstream behaviour, not something this image configures, and it bites in the container more than on a desktop because a pocket-dev session starts in `$HOME`, which is not a repo. Run the consult from inside the checkout (which is where a diff comes from anyway), or pass `--skip-git-repo-check` for a question with no material attached. DO NOT work around it by pre-trusting `/home/claude` in `~/.codex/config.toml`: the gate is what stops a consult from ranging over whatever happens to be in the home, and the home here holds every credential the container has. Nothing in this image writes that file (see above), so the temptation is a hand edit rather than a one-line change here — which does not make it a better idea.

**A consult run inside this checkout reads `AGENTS.md`, and that file is a POINTER at `CLAUDE.md`.** Claude Code reads `CLAUDE.md` and does NOT read `AGENTS.md`, even when `AGENTS.md` is the only instruction file present; codex reads `AGENTS.md` and does not read `CLAUDE.md`. Two harnesses, two filenames, and neither one reads the other's — so without the repo-root file a consult about the terminal runs with none of the two-layer alt-screen rules, the serialize/ansi_up ban, or the follow guard, which is exactly the material it needs in order not to recommend something already tried and reverted. Two full copies of the rules would be two BODIES drifting apart, and catching that drift needs a check that then also has to be maintained; a one-line pointer cannot drift. One FILE per harness is unavoidable, and that is the number that does not go down.

The pointer is load-bearing rather than decorative, and it was measured before being relied on: on codex-cli 0.153.0, 2026-09-08, with a prompt that never mentioned the rules at all, a rule placed inline in `AGENTS.md` was obeyed, a rule placed behind a pointer made the model read the pointed-to file first and then obey it, and an identical rule file that nothing referenced was ignored with no search. Both controls clean, so the positive result is not a model guessing what the asker wanted. That is model behaviour rather than a documented feature, so it is worth re-checking after a codex major bump alongside the calibration below. **DO NOT let `AGENTS.md` accumulate rules of its own**: the moment it says something `CLAUDE.md` does not, a Codex consult and a Claude session are running on different instructions, which is the failure the file was added to avoid. `test/server/codex.test.js` asserts the file exists at the repo root, names `CLAUDE.md`, and that its prose stays under 400 characters once the HTML comment is stripped — the comment explaining WHY it is a pointer is long and is not rules content, so it is excluded from the measurement rather than counted.

**Calibration, measured in this container** (2026-08-15, codex-cli 0.147.0, `gpt-5.6-sol`): the two-line `def pct(part, whole): return part / whole * 100` diff from `/second-opinion`'s calibration table, run through the directed consult, returned the documented `ZeroDivisionError` plus the `TypeError`, `OverflowError`, `inf` and bool-is-int findings. That is the check to re-run after a codex major bump, because it fails informatively: a setup that is broken returns nothing, and nothing is also what an undirected prompt returns.

**`--security-opt seccomp=unconfined` is in `ExtraParams` for codex, and removing it breaks `codex exec review` in a way that LIES.** Docker's default seccomp profile denies unprivileged `unshare(CLONE_NEWUSER)`, so bubblewrap cannot create a namespace, so every codex mode that must EXEC a command to gather its own material dies before reading anything. Measured 2026-08-15: Tower's kernel allows namespaces (`user.max_user_namespaces = 256276`, host root can `unshare`), the container got `EPERM`, and of the three candidate knobs only this one works. `apparmor=unconfined` is not the blocker at all, and `--cap-add SYS_ADMIN` gets past `unshare` only to fail on `pivot_root`.

The failure it prevents is the reason this is worth a security flag rather than a note. Without it:

```
bwrap: No permissions to create new namespace ...   (x3, each 0ms)
codex: "No findings could be identified because the repository inspection command failed"
```

Four of six such runs LED with "No findings were identified" and buried the abort in the second clause, so a reader skimming the first sentence records a clean review that never happened. **"I could not look" and "I looked and found nothing" must not be allowed to look alike**, and that is a property of the sandbox working, not of the prose.

**Why this specific loosening is acceptable here, and the case against it, because it is a real case.** For: the container already bind-mounts `/var/run/docker.sock`, which the README correctly calls host-root equivalent, so seccomp filtering is not the boundary protecting Tower and never was; and the direction is counter-intuitive but real, since turning the container's seccomp off is what lets codex turn ITS sandbox on.

Against, from a `/second-opinion` consult on this very change, and NOT paraphrased away because it is correct: seccomp applies to **every** process in the container, not only codex's bwrapped children, so this also drops Docker's filter for the node server, Claude, and anything else running here. Docker blocks `io_uring` in that profile specifically because of container-escape history, and uid 99 does not protect a shared kernel from an unprivileged syscall exploit. **The strongest form of the objection is about the future, not today**: if the docker socket is ever removed or fronted with a filtered proxy, that hardening would be silently undercut, because this flag would be left behind as a second escape path nobody re-examined. So the honest statement is that this flag is acceptable **only while the raw socket is mounted**, and **removing the socket is the event that should force this decision to be re-taken**, not a moment to celebrate.

Two narrower alternatives were tried and measured, not assumed:

- **`-c use_legacy_landlock=true`**, codex's own non-bwrap backend. It is already deprecated ("will be removed soon") and fails here anyway: `error applying legacy Linux sandbox restrictions: Sandbox(LandlockRestrict)`, and the answer file then reads "No findings could be verified", the same lie in a different costume.
- **A custom seccomp profile.** Rejected on maintenance grounds (it pins a private copy of Docker's default that rots silently as Docker updates), and note it would need MORE than the userns clone flags: the `SYS_ADMIN` experiment got past `unshare` only to fail on `pivot_root`, so the real allowlist has to be traced rather than guessed.

**DO NOT reach for `--privileged` or `--cap-add SYS_ADMIN` instead**: measured, neither one makes bwrap work, so they would buy strictly more privilege for strictly less function.

**Fixing the sandbox does NOT make `review` good, and do not read it that way.** With seccomp off, the same `pct` diff through bare `review` returned "No definite regression or actionable bug is evident", still missing the `ZeroDivisionError` the directed consult finds every time. That is the under-reporting `/second-opinion` already documents. What the flag buys is that a useless-but-honest answer stops being indistinguishable from a crash.

**The directed consult was never observed to need the sandbox, which is NOT the same as it being unable to.** Its material arrives piped on stdin, so in every measured run it answered without executing anything. But `codex exec` is agentic and may choose to read files or run commands, so "the piped path is immune" is an observation about the runs so far, not a property of the tool. Do not lean on it as a fallback for a container where the sandbox is broken; fix the sandbox.

## Lavish Editor — the review loop for HTML artifacts

`lavish-axi` is a CLI that turns an HTML file a session generated into something a human can point at. The agent runs it, gets a URL back, and the human opens that URL to annotate specific elements, edit Mermaid diagrams as whiteboards, and send the notes back; the agent collects them with `poll`. It replaces "here is a screenshot, tell me what to change" with pointing at the thing.

```sh
lavish-axi /coding/dump/plan/plan.html      # prints JSON containing the review URL
lavish-axi poll /coding/dump/plan/plan.html # long-poll until the human sends feedback
lavish-axi end /coding/dump/plan/plan.html  # agent-initiated end; a plain reopen still works
```

Installed by `npm install -g lavish-axi` in the Dockerfile. Same `/usr/local` reasoning and the same two traps as codex: `/home/claude` is a bind mount that ships EMPTY so an image-owned binary under it is masked, and `~/bin` is EARLIER on `PATH` than `/usr/local/bin` so a copy left there shadows the image's own forever. Unpinned on purpose, with `lavish-axi --version` in the build log — and subject to the same cache-hit freeze as codex, which the weekly `no-cache` build in `docker-publish.yml` is what thaws.

**Being reachable is a five-link chain and every link fails silently.** `test/server/lavish.test.js` guards the WIRING of all five, and deliberately not the service: nothing in it starts the real CLI, inspects the socket it actually binds, or reaches it through a published port, because none of that is available to the cat-based E2E suite. Those are covered by a live pass, recorded at the end of this section, and the split is the same one `MANUAL-VERIFICATION.md` exists for. `test/server/pdEnv.js` scrubs the whole `LAVISH_` prefix (alongside `PD_`) out of the environment it hands spawned scripts, for a bug it had already been bitten by once: inside a real pocket-dev tab `LAVISH_AXI_HOST` is exported, so an inherited one makes `entrypoint.sh`'s resolution block skip entirely and every stubbed-`hostname` case compares the live container's address against what the test set up. Green in CI, red only inside pocket-dev, which is where these tests get run at least as often.

1. **The port is defined once**, `ENV LAVISH_AXI_PORT` in the Dockerfile. `EXPOSE`, the `Lavish Editor Port` config in `pocket-dev.xml`, and `docker-compose.yml` all have to match it, and the test reads the ENV and checks the other three against it rather than repeating the number. **The number itself is the web terminal port PLUS ONE**, which is the whole reason for it: one port to remember, the neighbour is the other one. `lavish.test.js` pins that as arithmetic against the template's `WebUI Port` rather than as a second copy of the literal, because every other port assertion here is derived from the ENV, so changing the ENV moves both sides together and they would all stay green on a wrong value. (It is free rather than merely unused — it was pocket-dev's own mobile-input-bridge port until `4548bf8` removed that bridge.) The cost of moving off Lavish's built-in default, stated because it is a real one: at the default, a process that somehow never saw `LAVISH_AXI_PORT` still agreed with the published mapping by accident, whereas here it binds the default and is unreachable. That makes the `LAVISH_` forwarding below load-bearing for the PORT and not only for the address, and it is why the `docker exec` probe further down imports PID 1's whole `LAVISH_` environment rather than just the bind address.
2. **The port has to be published.** Unpublished, the review URL resolves only from inside the container, which is the one place nobody is holding a browser.
3. **The bind address is resolved at boot by `entrypoint.sh`, and both obvious values are wrong.** Left unset, Lavish binds `127.0.0.1` only — its automatic Tailscale binding finds nothing here, because there is no `tailscale` CLI in this container (dgvpn is a userspace tsnet proxy, not a tailscale client), so `detectTailscale` returns null. And **`LAVISH_AXI_HOST=0.0.0.0` is refused**: Lavish coerces a wildcard back to loopback (`isWildcardHost` in its `paths.js`) and its listen helper closes any socket reporting an all-interfaces address, so setting the wildcard reads as configuring exposure while keeping exactly the loopback behaviour it was meant to fix. What works is the container's OWN address: on a bridge network Docker's published-port DNAT rewrites the destination to it, so a listener on `eth0` receives traffic arriving at the host port. Verified live on Tower 2026-09-03 — a container bound only to its `eth0` IP with `-p` answered from the host's loopback, its LAN address, and its Tailscale address. **That reasoning is specific to the bridge network `pocket-dev.xml` declares.** Under `--network host` there is no DNAT and `-p` is ignored, so binding one host interface is arbitrary rather than right; under macvlan or a routed network the container address is reachable directly and no mapping is involved. Neither is a supported deployment here. On a container attached to SEVERAL networks there are several candidates and nothing inside can tell which one the mapping forwards to, so `entrypoint.sh` takes the first and warns on stderr naming what it picked and what else it saw. The address is assigned per container start and is not guaranteed stable across recreates (Docker often reuses one; nothing promises it), which is why this is a runtime `export` and not a Dockerfile `ENV`. An explicit `LAVISH_AXI_HOST` from the template wins and is NOT filtered: an operator pinning an interface is honoured, including values the guess would reject.
4. **`LAVISH_AXI_LINK_HOST` is what makes the printed URL openable.** Lavish writes the link host into every session URL, and with none set it falls back to the bind address, which on the default bridge is a `172.x` address that resolves nowhere outside the container. On Tower the deployed template supplies the chosen LAN hostname. The tailnet name and IP are also allowed, so an away-from-home link can use either.
5. **The Host allowlist has to accept whatever name you typed.** Lavish's DNS-rebinding guard 403s any request whose `Host` header is not loopback, the bind address, or the link host, and answers with a page naming the URL that does work. `LAVISH_AXI_ALLOWED_HOSTS` (whitespace-separated) adds the other names you might type — LAN IP, short hostname, Tailscale IP. A lone `*` disables the guard and is only for a server behind separate authentication.

**`entrypoint.sh`'s export reaches PID 1, and `server.js` carries it the rest of the way.** `buildTmuxSpawnArgs` forwards every `LAVISH_`-prefixed variable out of the server's own environment as `new-session -e` (`SESSION_ENV_PREFIX` in `server.js`), because a tmux server outlives its clients and `new-session` inherits the SERVER's environment: one that was already running from before the export — a `docker exec tmux` ahead of the first web session is enough to produce one — would hand every session an environment without it, and each of those sessions would bind Lavish to loopback, and now also to Lavish's own default port, behind a published mapping for neither. It forwards by PREFIX rather than by a list of names so that a second runtime-resolved Lavish variable cannot reintroduce this by being forgotten, and the only thing outside the prefix it forwards is `PATH` (a stale tmux-server `PATH` launches the wrong harness — see "Terminal replies across reconnects"). Nothing else, because widening it would put every secret in the server's environment on a tmux command line. An explicit per-session `env` still wins over a forwarded value: the `PD_*` values are computed per session, the forwards are process-wide.

**A direct `docker exec` does not inherit entrypoint exports.** When launching Lavish from outside the container, inspect its current bridge address and pass `docker exec -e LAVISH_AXI_HOST=<container-address>` to both open and poll. Without it, Lavish can start on loopback and print a plausible LAN URL that refuses connections. This was reproduced while preparing the 2026-09-09 review; passing the actual address made the same URL reachable without restarting pocket-dev. Do not pin that address in the deployment template: it changes when Docker recreates the container.

**Publishing that port serves the artifact and its local assets with NO authentication**, to anything that can reach the host port. The Host allowlist is DNS-rebinding protection and NOT authentication: a direct client simply sends an accepted `Host` header, which is exactly what the verification curl below does.

The case for accepting that: 7681 beside it is an unauthenticated terminal in a container mounting the docker socket, so for a peer that can reach both, its neighbour grants nothing that peer did not already have. The case against, which is real and should not be paraphrased away: it is still a SECOND remotely reachable server, with its own parser, its own file-read surface and a feedback-submission path, and a host firewall may well treat the two ports differently, so "the terminal is already exposed" is an argument about one reachability set and not about all of them. The honest rule is that it belongs exactly where 7681 already is and nowhere else, and that removing or fronting the terminal port is the event that should force this decision to be re-taken. To narrow it now, bind the host side of the mapping to one interface rather than loosening the allowlist.

**`LAVISH_AXI_NO_OPEN=1` is set because there is no browser in here.** Not load-bearing — Lavish catches the failed launch and downgrades its status from `opened` to `ready` — but without it every open shells out to `xdg-open`, waits for it to fail, and reports a status that misdescribes what happened.

**State lives in `~/.lavish-axi`**, which is inside the home mount, so sessions and queued feedback survive a recreate with no volume of their own. `~/.lavish-axi/server.log` is where the detached server's startup and crash output goes, and it is the first place to look when an open returns nothing. The server self-stops after `LAVISH_AXI_IDLE_TIMEOUT_MS` (default 30 minutes) with no browser and no poll attached, so a review left open overnight is gone in the morning unless a poll is holding it; `0` or `off` disables that.

**The CLI being installed and the agent knowing to use it are separate facts.** The npm package carries its own Agent Skill at `/usr/local/lib/node_modules/lavish-axi/skills/lavish/SKILL.md`, and Claude Code does not read that path. Skills are discovered from `~/.claude/skills`, which here is a bind-mounted git checkout of Jake's config repo — the image must not write into it, so the skill is installed there separately and is not part of this image.

**`docker exec` does NOT see the bind address, and that trap is in the diagnosis path rather than the product.** `export` in `entrypoint.sh` reaches PID 1 and everything descended from it, which is `server.js`, the tmux server it spawns, and therefore every session: that is the path that matters and it works. But `docker exec` builds its environment from the image's `Config.Env`, not from PID 1, so a `lavish-axi` run that way binds loopback and produces a URL nothing outside can open. Import PID 1's environment when probing from outside, so the probe tests what a session actually gets:

```sh
ssh tower "docker exec pocket-dev bash -c '
  set -a; . <(tr \"\\0\" \"\\n\" < /proc/1/environ | grep \"^LAVISH_\"); set +a
  printf \"<!doctype html><html><body style=background:#fff><h1>probe</h1></body></html>\" > /tmp/probe.html
  lavish-axi /tmp/probe.html'"
```

That prints JSON containing the URL with the link host already resolved. Then, from the host, confirm the published port reaches the listener:

```sh
curl -s -o /dev/null -w '%{http_code}\n' "http://<link-host>:7682/"
```

A `200` says something answered on that port and accepted that `Host`, which is the chain working end to end for that name; it is not proof that this image's CLI is what answered, so pair it with the title in the body (`<title><artifact name> · Lavish</title>`) rather than the status alone. A `403` is the Host allowlist rather than reachability, and its body names the URL that would have worked. A connection refused has several causes and loopback binding is only one: a wrong interface picked on a multi-network container, the server having idle-timed-out, no session ever opened, or the mapping absent. Check `LAVISH_AXI_HOST` in the session's environment and `/proc/net/tcp` in the container before blaming the port mapping.

**Measured on a container built from this code, 2026-09-03**, which is exactly what the guard tests deliberately do not cover:

- `PID 1` carried `LAVISH_AXI_HOST=172.17.0.65`, matching the container's `eth0`.
- A session created through `POST /sessions` saw the same value, which is the `new-session -e` forwarding working rather than inheritance happening to hold.
- A hostile `~/bin/hostname` printing `10.6.6.6` was planted and the container restarted; the bind address stayed `172.17.0.65`, so the absolute-path call really does keep a writable `~/bin` out of it.
- That session ran `lavish-axi` and got `status: opened` with a URL on the configured link host.
- `/proc/net/tcp` showed the listener on the container's own address and the configured port: neither loopback nor wildcard. That hex pair is the check worth knowing, since `awk 'NR>1{print $2}' /proc/net/tcp` prints `<addr>:<port>` big-endian hex, and 7682 is `1E02`.
- Fetching the printed URL from the host returned `200` and `<title>probe3 · Lavish</title>`; the LAN and tailnet addresses each returned `200`; a `Host: evil.example.com` returned `403`.
- The tailnet name resolves through the tailnet resolver (`dig @100.100.100.100 tower.note-mountain.ts.net` answers `100.103.123.19`) but NOT through Tower's own, which runs `--accept-dns=false`. It is in the allowlist rather than being the link host, so this only matters if someone types it: a failed `curl` from Tower for that name is Tower's resolver, not a wrong value.

## Common gotchas

- `<script type="module">` scopes everything inside to the module. Functions referenced from HTML `onclick="..."` attributes MUST be put on `window` explicitly. The `Object.assign(window, { ... })` block at the end of `index.html`'s script is load-bearing — `onclick-coverage.test.js` is the regression guard.
- Whole-screen copy reads the parsed xterm buffer, NOT a re-serialized ANSI stream. `serialize()` encodes gaps/tabs/never-written cells as cursor-move CSI (`\x1b[NC`, `\x1b[NG`), and any ANSI->HTML converter that only handles SGR (e.g. `ansi_up`) drops those and loses the spaces. This is why `@xterm/addon-serialize` and `ansi_up` were removed. Don't add them back for copy.
- xterm.js's `copyOnSelect: true` silently no-ops on HTTP (clipboard API requires a secure context). We do explicit `term.onSelectionChange` + `clipboardWrite` (with `execCommand` fallback) instead.
